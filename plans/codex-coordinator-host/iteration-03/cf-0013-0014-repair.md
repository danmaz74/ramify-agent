# I3 publication and early startup recovery repair

Assessment `as-0011` confirmed `cf-0012` resolved at candidate
`e4f665889b915fd2e337a10411e1c62c38b2499e`, with passing audit and independently
rerun focused tests. It identified two remaining startup windows: a permanent
successor could retain no job before listener failure (`cf-0013`), and record
publication before active-index publication could prevent further continuation
(`cf-0014`). This repair applies the requested KISS constraint.

| Responsibility | Before | After |
| --- | --- | --- |
| Permanent successor admission | Record written before known job adoption and task directions | Supplied job verified under service ownership; directions written before first generation record |
| Latest generation | Successor lookup and active-index predicates could disagree | One lookup of retained generation records resolves both exact admissions and latest committed owner; the index is only a hint |
| Recovery publication | A late index could block either predecessor selector | Ordinary next-generation publication advances the index after settlement and latest-owner validation; no separate repair protocol |
| MCP replacement | Every preceding generation name was added, including hosts that never created an endpoint | Preserve prior HTTP entries with their actual endpoints and explicit replacement choices; omit unused pre-listener generated names |

The generation record remains the sole durable admission. Exact command identity
and full argument hash still select the original admitted successor, including
stopped generations; changed arguments and new stale selectors remain refused.
The host uses the same lookup under existing service ownership before publishing
another generation. Conflicting successors, cycles and differing execution
identities remain errors. The lookup reads only small generation metadata, not
provider conversation history, and does not mutate state. The ordinary new host
writes its usual active hint. No index-repair protocol, admission side database,
placeholder configuration URL or replay engine was added.

A continuation record has its verified job from creation. Its task directions
precede irreversible admission, and a pending explicit fresh-context choice is
retained until a thread exists. If startup fails before listener/provider creation,
the failed successor can therefore be selected for another explicit resume while
preserving the original job, baseline and receipt lineage. A generated MCP name
from such a host was never installed: replacement excludes it rather than
fabricating a transport. Existing HTTP entries still use complete valid disabled
tables, and user-specified replacement choices remain intact. Provider permissions,
instructions and global configuration are unchanged.

The new exact registered native witness uses real CLI/service/Git/guardian
processes and a helper that pauses the actual first record write. It exercises:

- Host death before admission: no successor exists; concurrent identical retries
  admit exactly one continuation with the requested settings and task.
- Host death immediately after admission, before the active index changes:
  the index naturally still names A, status resolves committed B, exact retry
  retains B's uncertain startup outcome, a new A command is refused, and explicit
  resume(B) creates the next generation without manual retained-state edits.
- Injected listener failure after admission: exact retry observes failed B with
  its original job; explicit resume(B) succeeds without another registration.

Each path first admits a completed send and an unacknowledged send in A. The final
host retains their exact completed/uncertain outcomes, and retrying either leaves
provider history unchanged. All paths preserve original task plus added directions,
model/worker/assessor choices, explicit fresh context, replaced actual MCP entries,
the original job/baseline, and unchanged HEAD. Each has one assisted job. Guardian
settlement is observed before replacement. The fixture injects listener failure
and scripts provider/model protocol answers; processes, first-record crash windows,
filesystem publication, HTTP controls, ownership and settlement are real.

Existing multi-generation native regressions remain passing, including exact
resume retry after stop/later owners, argument conflicts, persistent history,
provider failure, unknown-delivery retention, orphan settlement and guardian-death
refusal. An ordinary regression additionally verifies an unknown supplied job
cannot publish any admission or construct a listener/provider and releases
ownership. This repair did not repeat or extend the separate live model pilot.
