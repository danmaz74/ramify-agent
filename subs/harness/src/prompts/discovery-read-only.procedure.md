## Harness role names

The toolkit's module-architect skill describes agents receiving architectural
evidence. Your harness role is the plan architect, module architect or capability
architect named in your role instructions. A module architect coordinates one
module work item; a module engineer implements a scoped iteration. The skill's
broader terminology does not change that assignment.

## Discovery with the active read tools

Use `read`, `grep` and `ls` with the paths supplied by the current task. Paths
in views and assignments are project-relative; resolve them from the declared
project root, rather than the tool's module-local working directory. Supplied
revision, coverage and unavailable details are authoritative delivery evidence;
do not search for metadata already supplied. Read metadata only for a specific
evidence question those details do not answer.

With an exact symbol or known owner, begin with that symbol in the owner's
bounded architect records or the consumer's relevant API view. Use `ls` on the
supplied root before assuming a child directory exists. API `children` and
`external` directories exist only where there is received evidence; never
guess an ordinary API owner directory. Name hidden generated roots explicitly
in `grep`'s path, then `read` the matching record or page. A known owner's
`module.json`, `behavior.jsonl` and relevant `tests.jsonl` are useful bounded
leads. Broaden to the architect map and domain terms only when those leads
do not answer the question. Do not infer semantic relevance or availability
from exposure counts, and do not set view-use quotas.

An ordinary API view and a testing API view establish access for their own
source areas; keep them separate. The architect view establishes behavior and
ownership, not consumer importability. Preserve all coverage limits: absence
under incomplete coverage cannot prove that behavior or access is absent.
Verify defining source for a specific remaining behavior question, including
a truncated signature, and cite the locations actually inspected.

This role has no shell. Use `grep` with an explicit path and bounded pattern
instead of shell `rg`; use `ls` to discover existing roots and `read` to inspect
bounded records when search output omits detail. It cannot refresh views,
create scratch worktrees or run a hypothetical provider check. State those
verification limits and use the supplied producer evidence. An authorized
module engineer or gate performs executable verification; a read-only judgment is
not that check.
